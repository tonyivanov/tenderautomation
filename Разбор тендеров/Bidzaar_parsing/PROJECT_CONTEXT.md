---

## Что это за проект

**Bidzaar-Scout** — внутренний инструмент компании **Git in Sky (ГИС, GitInSky)** для автоматического мониторинга тендерной площадки **Bidzaar** (https://bidzaar.com).

**Цель:** каждое утро узнавать, какие новые тендеры опубликовались, и вычленять из них те, которые подходят профилю ГИС, чтобы BD-команда не тратила часы на ручной просмотр сотен карточек.

**Состояние:** День 1 системы построен и работает в проде. День 2 (LLM-анализ через API) — отложен.

## Что такое Git in Sky (ГИС)

Это **DevOps / IT-infrastructure consultancy**. Клиенту они продают не «руки DevOps», а понятные бизнесу сценарии:

- где в инфраструктуре есть слабые места,
- выдержит ли система рост и пиковые нагрузки,
- можно ли быстро восстановиться после сбоя,
- где компания переплачивает за облако,
- как повысить устойчивость без лишних затрат.

**Целевые роли у клиентов:** CIO, CTO, IT Director, руководители инфраструктуры / платформ / эксплуатации.

**Партнёрский контекст:** часто фигурирует Cloud.ru, иногда в связке SberTech.

**Ключевые лица для PR / экспертного позиционирования:**

### Услуги ГИС

- аудит инфраструктуры
- оптимизация инфраструктуры и облачных затрат (FinOps)
- отказоустойчивость
- безопасность инфраструктуры
- резервное копирование и восстановление (DR)
- миграции (в облако, между облаками, на отечественный стек)
- поддержка инфраструктуры и dev-команд (DevOps-as-a-service)
- AI / ИИ-интеграции — как отдельное направление (помощь бизнесу внедрять AI прикладно, без иллюзий)

### Что НЕ делает ГИС (важно для отбраковки тендеров)

- Не поставщик железа. Тендеры на закупку «серверов Dell/HPE/Lenovo» без услуг — мимо.
- Не интегратор-дистрибьютор лицензий. Тендеры «закупка лицензий Cisco/Kaspersky» без внедрения — мимо, если нет партнёрства с этим вендором.
- Не разработчик прикладного ПО (1С, SAP, CRM, e-commerce платформы) — мимо.
- Не лицензированный обработчик ПДн / КИИ под ФСТЭК/ФСБ — если тендер требует лицензии, сначала проверить, есть ли у ГИС соответствующая.

## Архитектура решения

### Поток данных

```
Bidzaar (web)  →  fetch_list.py  →  SQLite (data/bidzaar.db)  →  prefilter.py
                                                                       ↓
                                                              export_for_review.py
                                                                       ↓
                                                          all_tenders.txt
                                                          score100_tenders.txt
                                                                       ↓
                                                       (человек кидает файлы Клоду в чат)
                                                                       ↓
                                                       Клод размечает кандидатов
                                                                       ↓
                                                       BD-команда читает ТЗ на сайте
```

### Ключевые файлы

| Файл | Что делает |
|------|------------|
| `auth.py` | Автологин в Bidzaar через Playwright. Первый раз — ручной вход в открывшемся окне; дальше всё авто. |
| `fetch_list.py` | Качает список активных тендеров. Использует `auth.py`. Инкрементальный синк. |
| `prefilter.py` | Прогоняет правила из `keywords.yaml` по полю `name` каждого тендера. Проставляет `prefilter_score`: 0 (отсев) / 50 (нейтрально) / 100 (кандидат). |
| `keywords.yaml` | Whitelist (что считать кандидатом) и blacklist (что отбраковывать). Можно править в Блокноте. |
| `export_for_review.py` | Выгружает базу в два txt-файла для разбора в чате с Клодом. |
| `1_setup.bat` / `2_fetch.bat` / `3_export.bat` | Удобные кнопки для не-разработчика. |

### Структура базы

Таблица `tenders` в SQLite:

- `id` (uuid от Bidzaar) — primary key
- `number` — внутренний номер тендера
- `name` — название (по нему работает префильтр)
- `company_name` — заказчик
- `publish_date` — когда опубликован
- `acceptance_end_date` — дедлайн подачи заявки
- `finish_date` — окончание процедуры
- `status`, `procedure_type`, `trading_type` — служебные коды Bidzaar
- `delivery_addresses` — JSON с адресами поставки
- `raw_json` — весь оригинальный JSON-ответ Bidzaar (на случай, если нужно вытащить что-то ещё)
- `fetched_at` — когда тендер последний раз попадал в синк
- `prefilter_score`, `prefilter_reason` — результат правил
- `details_fetched`, `llm_score`, `llm_verdict` — зарезервированы под День 2 (пока NULL)

## Технические детали Bidzaar (важно — не переоткрывать заново)

### Авторизация

Bidzaar **не использует OIDC-обёртку** для хранения токена. JWT лежит в `localStorage` под ключом `access_token` напрямую, как plain-строка. Срок жизни access-токена — 1 час (поле `exp` в payload JWT).

Также в localStorage есть ключ `id_token`. Refresh-токен через cookies или localStorage наружу не выставляется — silent-refresh браузер делает сам через ASP.NET cookie `.AspNetCore.Identity.Application`.

**Поэтому выбранная схема авторизации:** Playwright. Первый раз пользователь логинится в открытом окне Chromium, скрипт сохраняет состояние в `playwright_state.json` (cookies + localStorage). Дальше — headless, открыли страницу, прочитали свежий токен из localStorage, закрыли. Сессия живёт неделями.

### API endpoints

| Что | URL | Метод |
|-----|-----|-------|
| Список активных тендеров | `https://bidzaar.com/api/process/light/procedures/available` | GET |
| Детали тендера (позиции) | `https://bidzaar.com/api/process/light/procedures/read/{id}/versions/{version_id}/positions` | GET |
| Скачивание файла | `https://bidzaar.com/api/filestorage/files/download/{file_id}` | GET |
| Карточка тендера в браузере | `https://bidzaar.com/process/light/{id}` | (для людей, не API) |

**Внимание!** Шаблон URL карточки в браузере — `process/light/{id}`, **НЕ** `requests/public/buy/procedure/{id}`. Второй вариант 404.

### Параметры списка

```
?paging.page=1
&paging.size=25
&sorting.key=publishDate&sorting.direction=desc
&logic=and
&filters[0].operator=in&filters[0].field=status&filters[0].value=[1]      # статус «активный»
&filters[1].operator=eq&filters[1].field=procedureType&filters[1].value=1  # стандартные процедуры
```

### Заголовки

Помимо `Authorization: Bearer ...`, нужен `x-user-companyid` — берётся из cookie `x-company-id` (формат `uuid1%3Buuid2`, нужен второй uuid после `%3B`).

### Объёмы

Площадка держит **~2700-2900 активных тендеров одновременно**. За ночь добавляется ~100-150 новых. Темп комфортный для 1 запроса в секунду — без капчи и без агрессивного rate-limit.

## Как делать аналитику тендеров

Это самая ценная часть контекста. Систему построили специально потому, что keyword-фильтр **не понимает смысла** — а Клод понимает.

### Тестовый прогон (29 апреля 2026)

При первом полном запуске на 2769 тендеров:

- score=100 (кандидаты): 170 тендеров
- score=50 (нейтрально): 2377
- score=0 (отсев): 222

После ручного разбора Клодом:

- **реально интересных: 12** (из 170 кандидатов префильтра, ~7% точности)
- **утечек префильтра** (интересного в score=50): **0**

Вывод: префильтр аккуратно сужает выборку (170 из 2769 = 6%) и **золото не теряет**, но даёт много false positives. Финальный отбор делает Клод по семантике.

### Эшелоны кандидатов (используй такую же разбивку)

**⭐ Прямое попадание** — заходить с приоритетом:
- Аудит ИТ-инфраструктуры / архитектуры
- Миграция на Astra Linux + Postgres Pro (импортозамещение стека)
- Поддержка / модернизация Opensearch, ClickHouse, Kubernetes, других open-source стеков
- Облачные сервисы: разработка / поддержка / FinOps-оптимизация
- DR / резервное копирование (если про процессы и инфру, не про ПО)
- AI/ML внедрение — корпоративные ИИ-помощники, RAG-системы, ML-инфра

**🟡 Стоит изучить ТЗ** — может оказаться нашим, может нет:
- Закупка с услугами миграции (например, «закупка и миграция сетевого оборудования»)
- ИБ объектов КИИ (нужна лицензия ФСТЭК — проверить)
- Замена подсистемы виртуализации (если корп-инфра — да, если АСУ ТП — мимо)
- ASM / DSP / SOC SaaS — если ГИС перепродаёт чьё-то решение или интегрирует
- RFI (Request for Information) — не тендер, но попадание в long-list заказчика

**🟠 Тяжёлая конкуренция** — большие игроки, у них либо свои команды, либо устоявшиеся партнёры:
- билайн, МегаФон, МТС, Сбер, Яндекс — ГИС там скорее в роли субподрядчика
- Тендеры > 50 млн ₽ часто разыгрываются между крупными интеграторами

**🔴 Шум** — типичные ложные срабатывания префильтра:
- «контейнер» = морской / ЖБК / рефконтейнер (НЕ Docker!)
- «сервер» = поставка железа без услуг
- «Siemens» / «siem» = промышленные контроллеры
- «астра» = Астрахань, АльфаСтрахование (НЕ Astra Linux!)
- «мониторинг» = «мониторинг рынка / цен» (закупочный термин)
- «сопровождение» = 1С, SAP, CRM, авиаперевозки
- «восстановление» = ЛКМ цеха, освещение, фонтан
- «эксплуатация» = ОПО, инженерные системы
- «инфраструктура» = транспортная, железнодорожная

### Формат разметки для BD-команды

Когда Клод размечает список тендеров, выводить так:

```
**Заказчик** | Краткое название
🔗 https://bidzaar.com/process/light/{id}
⏰ дедлайн (если близко — выделить)
📊 Что закрывает из услуг ГИС, в чём угол захода. 1-2 предложения.
```

Группировать по эшелонам (⭐ → 🟡 → 🟠 → 🔴 без 🔴 в выводе, его опускаем).

В конце — **проверка на утечки**: пробежаться по `all_tenders.txt` (если он приложен) на ключевые слова, которые префильтр НЕ ловит, но которые могут указывать на профиль ГИС: `kubernetes`, `docker`, `terraform`, `ansible`, `prometheus`, `grafana`, `zabbix`, `postgres`, `clickhouse`, `mongodb`, `redis`, `kafka`, `elasticsearch`, `opensearch`, `vmware`, `openshift`, `it-инфра`, `ит-аудит`, `критич*инфра`, `импортозамещ`, `outstaff`, `аутсорсинг ит`, `выделенн*команд`. Если что-то пропущено — предложить добавить ключ в `keywords.yaml`.

## История принятых решений

Чтобы новый Клод не предлагал то, что уже отвергли, и не переделывал то, что уже сделано:

1. **Отказ от headless-первой архитектуры.** Сначала рассматривали Playwright как основной транспорт. Отказались: API проще, быстрее, надёжнее. Playwright оставили только для авторизации.

2. **Двухэтапная фильтрация.** Сначала дешёвый keyword-префильтр, потом дорогой LLM-анализ. Альтернатива (всё через LLM) рассмотрена и отвергнута: при 2700 тендеров на прогон это ~$10-30/раз, дорого без выигрыша в качестве — префильтр золото не теряет.

3. **SQLite вместо JSON или CSV.** Нужны индексы, дедуп по id, история, возможность SQL-запросов на лету.

4. **Куки + localStorage в одном `playwright_state.json`.** Потому что Playwright по умолчанию сохраняет и то, и другое; не надо городить кастомный экспорт.

5. **Все батники — чистый ASCII + CRLF.** Раньше в батниках была кириллица — Windows cmd ломалась на кодировке. Английские батники + русский в README. **Не возвращай кириллицу в .bat — всё сломается.**

6. **URL карточки в браузере** — `https://bidzaar.com/process/light/{id}`. Первая версия использовала `/requests/public/buy/procedure/{id}` — это 404. Не повторяй.

7. **Память пользователя про "вы".** В деловой переписке от имени ГИС обращаться к адресату на «вы» с маленькой буквы, без излишней официозности.

8. **Клод НЕ должен предлагать день 2 без явного подтверждения от пользователя.** В оригинальном диалоге уточняли: API-key есть или нет, готов ли тратить $5-15/мес. Без этого подтверждения остаёмся в режиме ручного разбора через чат.

## Что планировалось, но не реализовано (День 2)

Когда у заказчика появится Anthropic API key и желание тратить ~$5-15/мес:

1. **`fetch_attachments.py`** — для каждого тендера со score=100 скачивать ТЗ (PDF/DOCX/XLSX) в `data/attachments/{tender_id}/`.
2. **`extract_text.py`** — извлекать текст из файлов (pypdf, python-docx, openpyxl), складывать в новую колонку `attachments_text`.
3. **`analyze.py`** — отдавать каждый тендер с текстом ТЗ в Claude API (Sonnet для пограничных случаев, Haiku для массового потока). Системный промпт включает этот PROJECT_CONTEXT. Возвращать JSON: `{score, services_match, summary, red_flags, suggested_angle}`.
4. **`report.py`** — формировать ежедневный `interesting_tenders.txt` (дополняемый, не перезаписывающий).

Стоимость: ~$0.5-1.5 за прогон по 170 кандидатам, ~$5-15/мес при ежедневном запуске.

## Что важно при работе с пользователем

1. Пользователь — **не разработчик**. Инструкции пиши пошагово, без жаргона. Команды копируются и вставляются, не печатаются. Кнопки описывай конкретно («двойной клик на 2_fetch.bat»).
2. **Не оверинженирь** на ровном месте. Если можно решить yaml-конфигом — не пиши новый Python-модуль.
3. **Тестируй на реальных данных**, не на синтетике. Если есть `bidzaar.db`, подключайся к ней в Python и смотри.
4. **Если предлагаешь правки в коде — пересобирай архив** и презентуй файлом. Пользователь не редактирует код руками.
5. **Не упоминай память между чатами как данность.** В новом чате её нет. Контекст — только из этого файла.
