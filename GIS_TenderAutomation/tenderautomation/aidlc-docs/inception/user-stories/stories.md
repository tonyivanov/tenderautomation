# User Stories — TenderAutomation

Гранулярность: эпики (9 историй; исходные функциональные блоки дополнены контролем дедлайнов и reconciliation)
Acceptance criteria: смешанный формат — Given/When/Then для ключевых сценариев + чеклист

---

## Фазы реализации

| Фаза | Содержание | Stories |
|---|---|---|
| **Фаза 1 — Бэкенд** | Автосбор, квалификация, генерация JSONL + AGENTS.md, надёжное извлечение дедлайнов | US-01, US-02, US-03 (бэкенд-часть), US-08 |
| **Фаза 2 — Веб-интерфейс** | Просмотр, Архив, скачивание файлов для AI, загрузка результата анализа, решения, история | US-03 (UI-часть), US-04, US-05, US-06, US-07 |
| **Фаза 3 — Уведомления** | Telegram-уведомления, email-дайджест | Расширение US-04 |
| **Эксплуатационное восстановление** | Пакетное исправление существующих дедлайнов и Bidzaar-ссылок | US-09 |

## US-01: Автоматизированный сбор тендеров

**Фаза**: 1 — Бэкенд
**Персона**: Аналитик тендеров
**Приоритет**: Must Have
**Ссылки на требования**: FR-01, FR-02, FR-10

**История**:
> Как **аналитик тендеров**, я хочу чтобы система автоматически собирала новые тендеры со всех настроенных площадок по расписанию и при необходимости по запросу, чтобы **не тратить время на ручной мониторинг и гарантировать полноту выборки**.

### Acceptance Criteria

**Сценарий 1 — Плановый запуск по расписанию**
```
Given: Система настроена с расписанием cron и учётными данными для площадок в .env
When: Наступает запланированное время запуска
Then: Система автоматически подключается к каждой площадке
  And: Забирает только тендеры, появившиеся с момента последнего запуска (инкрементально)
  And: Сохраняет новые тендеры в хранилище
  And: Записывает результат запуска в лог (количество новых тендеров, статус, время)
```

**Сценарий 2 — Ручной запуск**
```
Given: Пользователь с правами аналитика или администратора
When: Пользователь инициирует ручной сбор через веб-интерфейс или CLI
Then: Система запускает сбор немедленно, независимо от расписания
  And: Результат доступен в течение 30 минут
```

**Сценарий 3 — Добавление новой площадки**
```
Given: Разработчик создал дескриптор новой площадки (YAML) и модуль-адаптер
When: Дескриптор помещён в директорию платформ и система перезапущена
Then: Новая площадка автоматически включается в цикл сбора
  And: Ядро системы не изменялось
```

**Чеклист**:
- [ ] Расписание cron настраивается без изменения кода
- [ ] Каждый запуск сохраняет метку времени последнего успешного сбора на каждой площадке
- [ ] При ошибке на одной площадке сбор на остальных продолжается
- [ ] Учётные данные хранятся только в `.env`, не в коде и не в логах
- [ ] Один полный цикл сбора завершается менее чем за 30 минут
- [ ] Поддерживается минимум 2 площадки: B2B-Center и Bidzaar

## US-02: Квалификационная фильтрация тендеров

**Фаза**: 1 — Бэкенд
**Персона**: Аналитик тендеров
**Приоритет**: Must Have
**Ссылки на требования**: FR-02, FR-03

**История**:
> Как **аналитик тендеров**, я хочу чтобы система автоматически квалифицировала собранные тендеры по настраиваемым YAML-фильтрам (ключевые слова + семантические правила), чтобы **видеть в интерфейсе только потенциально релевантные тендеры, не просматривая шум вручную**.

### Acceptance Criteria

**Сценарий 1 — Keyword-фильтрация (Tier 1)**
```
Given: Настроен keywords.yaml с whitelist/blacklist и весами
When: В хранилище появляется новый тендер
Then: Система вычисляет prefilter_score на основе совпадения ключевых слов
  And: Тендер с score > порога помечается как кандидат для дальнейшего анализа
  And: Тендер с score = 0 помечается как отфильтрованный (не показывается в основном списке)
```

**Сценарий 2 — Обновление фильтров**
```
Given: Аналитик отредактировал keywords.yaml (добавил/удалил слова)
When: Запускается следующий цикл квалификации
Then: Новые правила применяются ко всем новым тендерам
  And: Ретроспективная переквалификация (по запросу) возможна для существующих тендеров
```

**Чеклист**:
- [ ] YAML-формат фильтров расширен: поддерживает категории, веса, логические операторы
- [ ] Обратная совместимость с текущим `keywords.yaml`
- [ ] Фильтры редактируются без изменения кода и без перезапуска сервиса
- [ ] Семантические правила (Tier 2) описаны в формате, пригодном для AI-агента
- [ ] Результаты квалификации сохраняются с указанием применённых правил
- [ ] Защита от шумных выдач (>1000 лотов на запрос = пропуск)

## US-03: Скачивание данных для AI-анализа

**Фаза**: 1 — Бэкенд (генерация файлов) + 2 — Веб-интерфейс (скачивание)
**Персона**: Аналитик тендеров
**Приоритет**: Must Have
**Ссылки на требования**: FR-04, FR-06

**Контекст**: У компании нет централизованного AI-решения. Каждый специалист использует свой инструмент (claude.ai, ChatGPT, Gemini и др.). Система предоставляет стандартизированные файлы для загрузки в любой AI-инструмент.

**История**:
> Как **аналитик тендеров**, я хочу скачать из системы JSONL-файл с квалифицированными тендерами и файл инструкций AGENTS.md, загрузить их в свой AI-инструмент и получить анализ, чтобы **не тратить время на ручное копирование данных и получать структурированную оценку в любом удобном AI-сервисе**.

### Acceptance Criteria

**Сценарий 1 — Скачивание файлов из веб-интерфейса**
```
Given: Завершён цикл сбора и квалификации, есть новые квалифицированные тендеры
When: Аналитик нажимает «Скачать для AI-анализа» в веб-интерфейсе
Then: Система формирует архив или два файла: tenders.jsonl и AGENTS.md
  And: JSONL содержит тендеры прошедшие Tier 1, каждая строка — валидный JSON
  And: AGENTS.md содержит инструкции для AI-агента: схему данных, систему эшелонов, GIS-профиль
  And: Файлы скачиваются в браузере специалиста
```

**Сценарий 2 — Использование в AI-инструменте специалиста**
```
Given: Специалист скачал tenders.jsonl и AGENTS.md
When: Специалист загружает оба файла в свой AI-инструмент (claude.ai, ChatGPT, и др.)
Then: AI-агент читает AGENTS.md и понимает контекст без дополнительных объяснений
  And: Агент анализирует тендеры из JSONL и выдаёт структурированную квалификацию
  And: Никакой настройки под конкретный инструмент не требуется
```

**Сценарий 3 — Выборочная выгрузка**
```
Given: Аналитик просматривает список тендеров в веб-интерфейсе
When: Аналитик отмечает несколько конкретных тендеров и нажимает «Скачать выбранные»
Then: В JSONL включаются только отмеченные тендеры
  And: AGENTS.md остаётся неизменным
```

**Чеклист**:
- [ ] JSONL: одна строка = один тендер, каждая строка — валидный JSON
- [ ] Каждый объект содержит: id, platform, title, buyer, budget, deadline, description, url, prefilter_score, qualification_tier, exported_at
- [ ] AGENTS.md описывает: схему данных, систему эшелонов, GIS-профиль, инструкции по квалификации
- [ ] AGENTS.md не упоминает конкретные LLM-модели или провайдеров
- [ ] Доступна выгрузка всех новых тендеров или выбранных вручную
- [ ] Схема полей документирована и версионирована вместе с кодом

## US-04: Просмотр квалифицированных тендеров в веб-интерфейсе

**Фаза**: 2 — Веб-интерфейс
**Персона**: Аналитик тендеров, Менеджер BD
**Приоритет**: Must Have
**Ссылки на требования**: FR-05, FR-09, FR-ARCHIVE-01

**История**:
> Как **аналитик тендеров**, я хочу видеть актуальный список квалифицированных тендеров в браузере с индикаторами новых записей и стандартными карточками, чтобы **быстро находить непросмотренные тендеры и переходить к оригиналу на площадке**.

### Acceptance Criteria

**Сценарий 1 — Список с индикатором новых**
```
Given: Пользователь авторизован в системе
When: Пользователь открывает главную страницу
Then: Отображается список квалифицированных тендеров, отсортированных по дате (новые сверху)
  And: Непросмотренные тендеры помечены красной точкой
  And: После открытия карточки тендера красная точка исчезает
```

**Сценарий 2 — Карточка тендера (стандартный уровень)**
```
Given: Пользователь в списке тендеров
When: Пользователь кликает на тендер
Then: Открывается карточка с полями: название, заказчик, НМЦК, дедлайн, эшелон (если AI-анализ выполнен), краткое описание предмета, ссылка на оригинал на площадке, дата публикации
  And: Доступны кнопки действий: «Запустить AI-анализ», «Взять в работу», «Отклонить», «Отложить»
```

**Сценарий 3 — Уведомление в Telegram (Фаза 3)**
```
Given: Завершён цикл квалификации, появились новые кандидаты
When: Система отправляет уведомление
Then: В настроенный Telegram-канал/чат приходит сообщение с количеством новых тендеров и ссылкой
```

**Сценарий 4 — Активные очереди и Архив**
```
Given: Тендеры получили LLM-очередь P1 или P2 и имеют известные дедлайны
When: Аналитик открывает P1 или P2
Then: Тендеры с дедлайном раньше текущего времени не отображаются в активной очереди
  And: Просроченные тендеры доступны во вкладке «Архив»
  And: Недавно просроченные тендеры показаны первыми
  And: Вкладка «Все» продолжает показывать активные и архивные записи
```

**Сценарий 5 — Статус и неизвестный дедлайн**
```
Given: У тендера есть рабочий статус или дедлайн не удалось определить
When: Система формирует вкладки списка
Then: Попадание в Архив не изменяет статусы taken, deferred, rejected и другие
  And: Тендер без валидного дедлайна не считается просроченным
  And: Для неизвестного дедлайна явно отображается отсутствие даты
```

**Чеклист**:
- [ ] Веб-интерфейс требует авторизации (логин/пароль)
- [ ] Список поддерживает фильтрацию: по площадке, по статусу, по дате, по эшелону
- [ ] Список поддерживает поиск по названию и заказчику
- [ ] Интерфейс работает в Chrome, Firefox, Safari (современные версии)
- [ ] Интерфейс отзывчив на Windows и Mac/Linux
- [ ] Счётчик непросмотренных тендеров отображается в заголовке/badge
- [x] Вкладка «Архив» имеет точный счётчик и стабильный `data-testid`
- [x] P1/P2 исключают просроченные записи независимо от платформы
- [x] Сравнение дедлайна выполняется как сравнение timezone-aware значений с текущим UTC-временем
- [x] Каноническая ссылка на площадку остаётся доступной из активной очереди, Архива и карточки

## US-05: Загрузка результата AI-анализа в карточку тендера

**Фаза**: 2 — Веб-интерфейс
**Персона**: Аналитик тендеров
**Приоритет**: Should Have
**Ссылки на требования**: FR-06

**Контекст**: Специалист получает AI-анализ в своём инструменте (claude.ai, ChatGPT и др.) и опционально сохраняет результат в системе, чтобы он был виден коллегам и зафиксирован в истории.

**История**:
> Как **аналитик тендеров**, я хочу вставить результат AI-анализа (эшелон и обоснование), полученный в своём AI-инструменте, в карточку тендера в системе, чтобы **коллеги видели оценку и она хранилась вместе с историей тендера**.

### Acceptance Criteria

**Сценарий 1 — Загрузка результата анализа**
```
Given: Аналитик получил AI-оценку тендера в своём инструменте (claude.ai, ChatGPT и др.)
When: Аналитик открывает карточку тендера и нажимает «Добавить AI-анализ»
Then: Открывается форма с полями: эшелон (выбор из ⭐/🟡/🟠/🔴) и текст обоснования
  And: После сохранения анализ отображается в карточке тендера
  And: Фиксируется: кто добавил, через какой инструмент (опционально), когда
```

**Сценарий 2 — Просмотр анализа коллегами**
```
Given: Аналитик добавил AI-анализ к тендеру
When: Менеджер или другой аналитик открывает карточку тендера
Then: Результат анализа виден в карточке: эшелон, обоснование, автор, дата
  And: Менеджер может принять решение на основе этой информации
```

**Сценарий 3 — Обновление анализа**
```
Given: В карточке уже есть AI-анализ
When: Аналитик добавляет новый анализ (например, от другого AI-инструмента)
Then: Новый анализ сохраняется как актуальный, предыдущий остаётся в истории карточки
```

**Чеклист**:
- [ ] Поле эшелона — выбор из фиксированного списка: ⭐ прямое попадание / 🟡 стоит изучить / 🟠 тяжёлая конкуренция / 🔴 шум
- [ ] Поле обоснования — свободный текст, минимум 1 символ, максимум 2000 символов
- [ ] Поле «AI-инструмент» — необязательное (claude.ai, ChatGPT, Gemini, другое)
- [ ] Загрузка анализа опциональна — тендер можно взять в работу и без анализа
- [ ] Анализ сохраняется и виден всем авторизованным пользователям системы
- [ ] История изменений анализа доступна в карточке тендера

## US-06: Принятие решений по тендерам и ведение лога

**Фаза**: 2 — Веб-интерфейс
**Персона**: Менеджер BD, Аналитик тендеров
**Приоритет**: Must Have
**Ссылки на требования**: FR-05, FR-07

**История**:
> Как **менеджер BD**, я хочу фиксировать решение по каждому тендеру (взять в работу / отклонить / отложить) с заметкой через веб-интерфейс, чтобы **вести прозрачный audit trail и не возвращаться к уже рассмотренным тендерам**.

### Acceptance Criteria

**Сценарий 1 — Фиксация решения**
```
Given: Пользователь открыл карточку тендера
When: Пользователь нажимает «Взять в работу» (или «Отклонить», или «Отложить»)
Then: Система запрашивает необязательную заметку
  And: После подтверждения фиксирует: тендер ID, площадка, решение, заметка, пользователь, timestamp
  And: Тендер меняет статус в интерфейсе
  And: Запись немедленно появляется в логе действий
```

**Сценарий 2 — Конкурентная запись**
```
Given: Два специалиста одновременно работают с системой
When: Оба фиксируют решение по разным тендерам одновременно
Then: Обе записи корректно сохраняются в лог без конфликтов
  And: Каждая запись содержит идентификатор пользователя
```

**Чеклист**:
- [ ] Возможные решения: «Взять в работу», «Отклонить», «Отложить»
- [ ] Заметка — необязательное поле, максимум 500 символов
- [ ] Лог хранится в формате JSONL (append-only)
- [ ] Поддерживается конкурентная запись от нескольких пользователей
- [ ] Решение можно изменить (добавляется новая запись с пометкой «изменено»)
- [ ] Лог доступен для просмотра в веб-интерфейсе и для экспорта

## US-07: История обработанных тендеров

**Фаза**: 2 — Веб-интерфейс
**Персона**: Менеджер BD, Аналитик тендеров
**Приоритет**: Should Have
**Ссылки на требования**: FR-08

**История**:
> Как **менеджер BD**, я хочу просматривать историю всех обработанных тендеров с фильтрацией и поиском, чтобы **анализировать паттерны решений и быстро находить ранее рассмотренный тендер**.

### Acceptance Criteria

**Сценарий 1 — Просмотр истории**
```
Given: Пользователь авторизован
When: Пользователь переходит в раздел «История»
Then: Отображается список всех тендеров, по которым принято решение, с сортировкой по дате решения (новые сверху)
  And: Для каждого тендера видны: название, заказчик, площадка, решение, кто решил, когда
```

**Сценарий 2 — Фильтрация и поиск**
```
Given: Пользователь в разделе «История»
When: Пользователь применяет фильтр (по площадке, по решению, по дате, по пользователю)
Then: Список обновляется, показывая только соответствующие тендеры
  And: Поиск по названию и заказчику работает совместно с фильтрами
```

**Чеклист**:
- [ ] История хранит все тендеры: прошедшие фильтр, квалифицированные, с решениями
- [ ] Фильтры: площадка, статус (новый/в работе/отклонён/отложен), период, пользователь
- [ ] Поиск по названию тендера и заказчику
- [ ] Экспорт истории в JSONL (весь период или отфильтрованный)
- [ ] История доступна только авторизованным пользователям
- [ ] Производительность: список до 10 000 записей отображается без задержек

## US-08: Надёжное получение дедлайна

**Фаза**: 1 — Бэкенд
**Персона**: Аналитик тендеров
**Приоритет**: Must Have
**Ссылки на требования**: FR-DEADLINE-01, FR-DEADLINE-02, FR-DEADLINE-03, FR-DEADLINE-04

**История**:
> Как **аналитик тендеров**, я хочу чтобы система сохраняла подтверждённую дату окончания приёма заявок и находила её в карточке при отсутствии в выдаче, чтобы **не пропускать действующие тендеры и не тратить время на уже завершённые**.

### Acceptance Criteria

**Сценарий 1 — Структурированный дедлайн имеет приоритет**
```
Given: Выдача B2B-Center или Bidzaar API содержит валидный дедлайн
When: Адаптер преобразует запись в TenderModel
Then: Дедлайн разбирается строго и сохраняется как timezone-aware datetime
  And: Detail page для этого тендера не открывается
  And: В raw_data записывается источник дедлайна listing или api
```

**Сценарий 2 — Поиск даты в карточке**
```
Given: Дедлайн в выдаче или API отсутствует либо имеет недопустимый формат
When: Коллектор обрабатывает тендер
Then: Коллектор открывает каноническую карточку тендера в существующей HTTP или браузерной сессии
  And: Извлекает только явно обозначенную дату окончания приёма заявок или торгов
  And: Сохраняет источник дедлайна detail
```

**Сценарий 3 — Безопасная частичная ошибка**
```
Given: Карточка вернула 404, CAPTCHA, ошибку авторизации, timeout или неизвестную разметку
When: Detail-page fallback не смог подтвердить дедлайн
Then: Тендер сохраняется с deadline = null
  And: Другие тендеры и второй транспорт B2B-Center продолжают обрабатываться
  And: Лог содержит только площадку, tender ID, этап и безопасную категорию ошибки
```

**Чеклист**:
- [x] Невалидные, невозможные и неоднозначные даты не угадываются
- [x] Дата публикации и другие даты события не подменяют дедлайн
- [x] B2B-Center сохраняет endpoint и Playwright как два независимых транспорта
- [x] Bidzaar URL нормализуется в `https://bidzaar.com/app/process/light/{external_id}`
- [x] Detail URL ограничен настроенным доменом площадки
- [x] Detail lookup имеет timeout, rate limit и не выполняется при уже валидной дате
- [x] Example-based тесты покрывают известные форматы и ошибки
- [x] Hypothesis проверяет произвольный текст, timezone-границы и идемпотентность нормализации

## US-09: Reconciliation существующих тендеров

**Фаза**: Эксплуатационное восстановление
**Персона**: Администратор системы
**Приоритет**: Must Have
**Ссылки на требования**: FR-ARCHIVE-02, FR-DEADLINE-02, FR-DEADLINE-04

**История**:
> Как **администратор системы**, я хочу пакетно исправлять существующие тендеры без дедлайна и нерабочие Bidzaar-ссылки через `/admin` или CLI, чтобы **очистить production-очереди без прямого изменения БД и без остановки сбора**.

### Acceptance Criteria

**Сценарий 1 — Защищённый запуск из admin panel**
```
Given: Администратор авторизован и существуют записи, требующие reconciliation
When: Администратор запускает действие с допустимым размером пакета
Then: Система обрабатывает не больше заданного количества записей
  And: Показывает количество проверенных, обновлённых, оставшихся без дедлайна и ошибочных записей
  And: Не меняет workflow status тендеров
```

**Сценарий 2 — Эквивалентный запуск через CLI**
```
Given: Оператор имеет доступ к production CLI и конфигурации приложения
When: Оператор запускает reconciliation с тем же размером пакета
Then: Применяются те же правила выбора, нормализации URL и извлечения дедлайна
  And: Результат содержит те же безопасные счётчики
```

**Сценарий 3 — Повторный запуск**
```
Given: Один пакет уже был успешно обработан
When: Администратор повторяет reconciliation
Then: Уже нормализованные данные не изменяются повторно
  And: Не создаются дубликаты действий или тендеров
  And: Ошибка одного тендера не откатывает успешные обновления остальных
```

**Чеклист**:
- [x] Admin action требует серверной проверки роли `admin`
- [x] Размер пакета валидируется и имеет безопасную верхнюю границу
- [x] Операция идемпотентна и безопасна для повторного запуска
- [x] Старые Bidzaar-ссылки заменяются каноническими ссылками по `external_id`
- [x] Секреты, cookies, токены и тела внешних ответов не попадают в лог или UI
- [x] Unit/integration-тесты покрывают пустой backlog, частичные ошибки и повторный запуск
