# Документ требований — TenderAutomation

## Intent Analysis

| Параметр | Значение |
|---|---|
| **Тип запроса** | Рефакторинг + Новая функциональность + Enhancement (значительный архитектурный разворот) |
| **Скоуп** | Системный — затрагивает все компоненты + создание новых (веб-интерфейс, сервер, уведомления) |
| **Сложность** | Высокая — полное переплатформирование с CLI-инструментов на серверное веб-приложение |

### Исходный запрос пользователя (verbatim)

> "Инструмент должен автоматически обрабатывать новые тендеры на разных площадках (сейчас b2bcenter & bidzaar), квалифицировать их по утвержденным и изменяемым фильтрам (желательно на формальном языке, например YAML), затем предоставлять информацию по отобранным тендерам в машиночитаемом виде для анализа агентом ИИ. Этот агент предоставляет анализ специалисту, который принимает решение, запускать ли процесс подготовки к участию в тендере или нет. Информация о тендерах, взятых в работу должна записываться в лог. Кроме того, нужно вести лог по обработанным и квалифицированным тендерам, с возможностью последующего анализа (в СУБД или в другом формате). Текущую реализацию надо нормализовать на reusable blocks, отличия в работе площадок фиксировать в файлах описания площадок, описания АПИ и т.п. Специалист с ИИ-агентом может работать в Windows или Mac/Linux."

### Ключевой архитектурный вывод

Система переплатформируется с двух независимых CLI-конвейеров (`b2bcenter-scout`, `bidzaar-scout`) в **единое серверное веб-приложение**, работающее на Linux VPS. Специалисты взаимодействуют с системой через браузер (Windows или Mac/Linux). Это не просто рефакторинг — это создание нового продукта на основе существующих алгоритмов.

## Функциональные требования

### FR-01: Автоматизированный сбор тендеров

- Система ДОЛЖНА автоматически собирать новые тендеры с настроенных площадок по расписанию (cron на Linux-сервере)
- Ручной запуск сбора ДОЛЖЕН поддерживаться (через веб-интерфейс или CLI на сервере)
- Текущие платформы: B2B-Center (HTML-скрейпинг) и Bidzaar (JSON API)
- Каждый цикл сбора ДОЛЖЕН быть инкрементальным (только новые тендеры с момента последнего запуска)
- Конфигурация расписания ДОЛЖНА быть изменяемой без изменения кода

### FR-02: Слой абстракции площадок

- Каждая тендерная площадка ДОЛЖНА быть описана файлом-дескриптором (YAML): метод доступа, метод аутентификации, эндпоинты, маппинг полей, ограничения (rate limits, антибот-паузы)
- Общий (reusable) код ДОЛЖЕН быть вынесен в shared-модули: HTTP-клиент, управление сессиями, операции с хранилищем, движок фильтрации
- Специфичный для площадки код ДОЛЖЕН быть изолирован в модуле-адаптере площадки
- Добавление новой площадки ДОЛЖНО требовать только: (1) файл-дескриптор, (2) модуль-адаптер — без изменений в ядре

### FR-03: Двухуровневая система квалификационных фильтров

**Уровень 1 — Keyword-фильтр (быстрый):**
- Расширенный YAML-формат: whitelist/blacklist ключевых слов с весами, категориями, логическими операторами (AND/OR/NOT)
- Сохраняет обратную совместимость с текущим `keywords.yaml`
- Работает локально, не требует вызова внешних API

**Уровень 2 — Семантические правила (для AI-агента):**
- YAML-правила с условиями по полям тендера (заказчик, НМЦК, тип закупки, ключевые слова, регион)
- Правила служат инструкцией/контекстом для AI-агента при финальной квалификации
- Описываются в `AGENTS.md` как часть инструкций агенту

Фильтры ДОЛЖНЫ быть редактируемыми специалистом без изменения кода.

### FR-04: Машиночитаемый вывод для AI-агента

- Квалифицированные тендеры ДОЛЖНЫ экспортироваться в формате **JSONL** (JSON Lines, один тендер на строку)
- Файл **`AGENTS.md`** ДОЛЖЕН быть создан и содержать:
  - Схему данных JSONL-файла с описанием всех полей
  - Семантику полей и системы оценки
  - Инструкции для AI-агента по интерпретации данных и квалификации тендеров
  - Правила эшелонирования (прямое попадание / стоит изучить / тяжёлая конкуренция / шум)
- `AGENTS.md` ДОЛЖЕН быть LLM-agnostic (не привязан к Claude или конкретной модели)
- `AGENTS.md` и схема данных ДОЛЖНЫ версионироваться в репозитории

### FR-05: Веб-интерфейс для специалистов

Веб-приложение ДОЛЖНО предоставлять специалистам:
- **Список квалифицированных тендеров** с индикатором «новый» (красная точка для непросмотренных)
- **Карточку тендера** с деталями и результатом анализа AI-агента
- **Кнопки действия**: «Взять в работу», «Отклонить», «Отложить», с полем для заметки
- **Историю/лог** обработанных тендеров с фильтрацией и поиском
- **Настройки фильтров** — редактирование YAML-фильтров через веб (или прямой доступ к файлу)
- Веб-интерфейс ДОЛЖЕН работать в любом современном браузере (Chrome, Firefox, Safari) на Windows и Mac/Linux
- Веб-интерфейс ДОЛЖЕН поддерживать нескольких одновременных специалистов

### FR-06: Интеграция AI-агента (decentralized / bring-your-own-AI)

- Система НЕ вызывает AI-агента напрямую — специалист использует свой AI-инструмент (claude.ai, ChatGPT, Gemini и др.)
- Система ДОЛЖНА предоставлять готовые файлы для загрузки: `tenders.jsonl` + `AGENTS.md`
- Специалист МОЖЕТ опционально загрузить результат AI-анализа (эшелон + обоснование) обратно в карточку тендера через веб-интерфейс
- Результат анализа ДОЛЖЕН быть виден всем авторизованным пользователям системы
- Система ДОЛЖНА быть LLM-agnostic: AGENTS.md описывает интерфейс без привязки к конкретному провайдеру
- **Обоснование**: у компании нет централизованного AI-решения, каждый специалист пользуется своим инструментом

### FR-07: Лог «взят в работу»

При пометке тендера специалистом как «взят в работу» ДОЛЖНО фиксироваться:
- ID тендера и площадка
- Идентификатор специалиста
- Временная метка (ISO 8601)
- Решение (взят / отклонён / отложен)
- Опциональная заметка

Лог ДОЛЖЕН:
- Храниться в формате **JSONL** (append-only)
- Поддерживать конкурентную запись от нескольких специалистов
- Быть доступен через веб-интерфейс

### FR-08: Лог обработанных и квалифицированных тендеров

- Все обработанные тендеры (прошедшие и не прошедшие фильтр) ДОЛЖНЫ сохраняться
- Формат хранения: **JSONL** (append-only для истории + SQLite для индексированных запросов)
- История ДОЛЖНА быть доступна для фильтрации и поиска в веб-интерфейсе
- Данные ДОЛЖНЫ поддерживать экспорт для внешнего анализа

### FR-09: Уведомления

- **Веб-интерфейс**: индикатор новых тендеров (красная точка / счётчик) для непросмотренных квалифицированных тендеров
- **Telegram**: уведомление при появлении новых квалифицированных тендеров (настраиваемые получатели)
- **Email**: ежедневный дайджест с перечнем тендеров, требующих квалификации
- Каждый канал уведомлений ДОЛЖЕН быть включаемым/отключаемым независимо
- Получатели ДОЛЖНЫ быть настраиваемыми без изменения кода

### FR-10: Автоматическая аутентификация на площадках

- Учётные данные площадок ДОЛЖНЫ храниться в `.env` файле на сервере (не в коде)
- Аутентификация ДОЛЖНА выполняться автоматически по сохранённым учётным данным
- Сессионные токены ДОЛЖНЫ кэшироваться и обновляться автоматически
- Ручной логин через Playwright НЕ ДОЛЖЕН требоваться в штатном режиме
- Метод аутентификации для каждой площадки ДОЛЖЕН описываться в файле-дескрипторе площадки

## Нефункциональные требования

### NFR-01: Расширяемость на новые площадки

- **Цель**: добавление новой простой API-площадки за < 1 рабочей недели одним разработчиком
- **Требование**: добавление площадки НЕ ДОЛЖНО требовать изменений в ядре — только дескриптор + адаптер
- **Горизонт**: первая новая площадка ожидается в ближайшие 1–3 месяца

### NFR-02: Развёртывание

- **Сервер**: Linux VPS/сервер (удалённый)
- **Планировщик**: cron на Linux
- **Клиентский доступ**: веб-браузер (Windows и Mac/Linux)
- Серверная часть НЕ ДОЛЖНА требовать запуска на клиентских машинах специалистов

### NFR-03: Производительность

- Полный цикл сбора и квалификации ДОЛЖЕН завершаться в течение 30 минут
- Время отклика веб-интерфейса: < 2 сек для списковых представлений, < 5 сек для карточки тендера

### NFR-04: Безопасность (Security Baseline — ВКЛЮЧЁН)

Применяются все правила Security Baseline (SECURITY-01 — SECURITY-15) как блокирующие ограничения:
- Учётные данные ТОЛЬКО в `.env` — никогда в исходном коде (SECURITY-12)
- Веб-интерфейс ДОЛЖЕН требовать аутентификации (SECURITY-08)
- Всё взаимодействие ТОЛЬКО по HTTPS / TLS 1.2+ (SECURITY-01)
- HTTP security headers на всех HTML-эндпоинтах (SECURITY-04)
- Структурированное логирование без секретов и PII (SECURITY-03)
- Защита от brute-force на форме входа (SECURITY-12)
- Зависимости пинятся точными версиями, lock-файл в репозитории (SECURITY-10)

### NFR-05: Тестирование (Property-Based Testing — ВКЛЮЧЁН)

Применяются все правила PBT (PBT-01 — PBT-10) как блокирующие ограничения:
- **Фреймворк**: Hypothesis (Python)
- **Приоритетные цели PBT**: парсинг YAML-фильтров, JSONL-сериализация/десериализация, логика скоринга тендеров, маппинг полей адаптеров площадок
- PBT ДОЛЖЕН быть включён в CI-пайплайн с логированием seed
- Совокупное line coverage production-кода в `src/`, измеренное `coverage.py` через `pytest-cov`, ДОЛЖНО быть не ниже **60%**
- Локальная merge-проверка и GitLab CI ДОЛЖНЫ завершаться ошибкой при покрытии ниже 60%
- Повышение покрытия ДОЛЖНО достигаться проверками поведения и ошибок, а не исключением непокрытого production-кода из измерения без отдельного утверждённого обоснования

### NFR-06: Кроссплатформенность клиента

- Веб-интерфейс ДОЛЖЕН работать в Chrome, Firefox, Safari (современные версии)
- Клиентское приложение не требуется — только браузер

### NFR-07: Сопровождаемость

- Shared-код выносится в `core/` модуль
- Адаптеры площадок реализуют общий интерфейс/протокол
- Поведение платформ управляется дескрипторами, не кодом

## Ограничения и допущения

1. **Playwright для аутентификации**: переход с ручного Playwright-логина на автоматический (.env) технически выполним для обеих площадок — детали в дескрипторах площадок
2. **JSONL как основной формат лога**: используется для append-only истории; SQLite опционально для индексированных запросов
3. **AI-агент**: не привязан к конкретному LLM-провайдеру; взаимодействие описано в `AGENTS.md`
4. **Текущие алгоритмы**: keyword-фильтрация, скоринг, инкрементальный сбор — сохраняются и переносятся в нормализованную архитектуру
